# Slabwatch

Forecast where this month's electricity units will end, **before** the 200-unit cliff.

Pakistani household consumers who stay at or under 200 units a month are "protected" and pay a much lower
per-unit rate. Going over once can cost that status for six months. Slabwatch takes a few meter readings (typed or
a photo Gemma reads), predicts the end-of-cycle units as a P10 / P50 / P90 band with TabPFN, and plain code
decides whether to say anything. If the chance of crossing is meaningful you get one message with a daily budget:

> You've used 141 units in 19 days. To stay under 200 you have 5.4 units/day for 11 days; you're running at 7.4.

Otherwise it stays quiet.

## The 200-unit rule (sources; assumptions may have changed)
- "A protected consumer who exceeds the 200-unit threshold even once during a six-month period will lose their
  protected consumer status": [Pakistan Observer](https://pakobserver.net/protected-electricity-consumers-face-new-tough-200-unit-billing-rules/).
- Rates: roughly Rs 10-13.5/unit protected vs about Rs 39 regular, [Daily Pakistan, 2026-08-03](https://en.dailypakistan.com.pk/03-Aug-2026/protected-vs-non-protected-electricity-rates-in-pakistan-for-200-units-2026-update).
- Origin: [NEPRA 2021 determination](https://www.nepra.org.pk/tariff/Tariff/Ex-WAPDA%20DISCOS/2021/TRF-100%20Determination%20XWDISCOs%2023-09-2021%2037543-45.PDF)
  ("consuming < 200 kWh per month consistently for the past 6 months").
- **Proposals exist** to cap the penalty at one month or raise the limit to 301 units ([Pakistan Observer](https://pakobserver.net/?p=777578)).
  Whether either has been notified was not verified as of 2026-10-24. The limit and penalty are settings
  (`SLAB_THRESHOLD`, `PENALTY_MONTHS`) and every message states which rule it assumed.

The forecast is in **units**, which the household controls. The rupee price per unit moves every month (fuel charges
adjustment), so rupees are only an estimate.

## Quickstart
```bash
python3.11 -m venv .venv && . .venv/bin/activate
pip install -e ".[dev,data]"          # add [local] for TabPFN-3.5 on the laptop (pulls torch)
cp .env.example .env                  # every key is optional; doctor says what each unlocks
python -m slabwatch doctor
python -m slabwatch fetch-data --houses 1-10   # PRECON from Open Data Pakistan (46 MB)
python -m slabwatch build-features
python -m slabwatch backtest --models naive,last_ratio,gbm          # no keys needed
python -m slabwatch forecast --cycle-start 2026-10-05 --start-reading 10000 --reading 2026-10-24=10141
python -m slabwatch serve             # http://localhost:8000
pytest -q
```
Other commands: `add-reading`, `worker`, `start-cycle`, `db-init`, `fetch-bill`, `tariff-watch` (see `--help`).

## How it works
- **Data:** PRECON (LUMS, e-Energy '19), 1-minute whole-house power for Lahore homes 2018-19, CC0, aggregated to
  daily kWh. Training rows = 30-day windows x cut days 5..25. See [docs/DATA.md](docs/DATA.md).
- **Target:** `final_units / (units_so_far / days_elapsed x 30)`, the ratio to the multiply-it-out estimate. It is
  scale-free, so big PRECON homes still teach the shape of a cycle.
- **Model:** the mean of gradient-boosting and TabPFN quantiles (TabPFN through Prior Labs' API via `tabpfn-client`),
  calibrated on the dev homes; it won the pre-registered test ([docs/PROTOCOL-RESULTS.md](docs/PROTOCOL-RESULTS.md)).
  A local TabPFN-3.5 backend exists but was too slow on CPU, so no reported number uses it. P(cross) comes from the
  predicted quantiles.
- **Decision:** `slabwatch/decide.py`: safe / watch / unsure / act / already_over. Code, not a model.
- **Reading:** Gemma reads meter photos and bills into strict JSON and refuses when it can't read.
- **Runtime:** Render web service (`render.yaml`), Temporal cycle workflow, PITC bill fetch (form post from a home connection),
  Browserbase tariff watch (FCA news), Tiger Cloud Postgres with hybrid search. See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

Backtest numbers live only in [docs/RESULTS.md](docs/RESULTS.md) (generated by the script). Demo runs (meter
photos, a sample bill, replayed households) are in [docs/SESSION.md](docs/SESSION.md).

## Honesty notes
- PRECON homes are larger than a typical protected household: median 30-day totals for houses 1-10 run from 214 to
  1271 units. The ratio target is meant to transfer; that is an assumption, checked only by error-by-size tercile.
- The backtest's `actual` weather mode uses the real temperatures of the remaining days as a stand-in for a
  forecast, which is optimistic. The `clim` mode (2008-2017 climatology) is the no-skill bound. Both are reported.
- The protocol scores the cliff call against a synthetic threshold (each house's median cycle total). Across all 41
  homes some cycles do end near 200, so [docs/SESSION.md](docs/SESSION.md) also scores the real 200-unit rule on the
  test-home cycles that end within 40 units of it, with a model fitted on the dev homes only. That is a replay of
  recorded homes, not a live family.
- A live cycle can't be scored before the contest deadline; the live demo shows a prediction and its due date.
